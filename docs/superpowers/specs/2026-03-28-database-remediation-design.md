# TuskerBrain Database Remediation Design

**Date**: 2026-03-28
**Scope**: `database/`, `core/repositories/`, `electron/ipc/`, seeders
**Approach**: Surgical Remediation — fix each issue at its source in dependency order
**Status**: Approved

---

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Schema authority | Drizzle-only (`schema.ts`) | Single source of truth, eliminates DDL drift |
| Timestamp convention | Milliseconds (`mode: 'timestamp_ms'`) | Matches existing seed data and DDL defaults, no data migration |
| Async wrappers | Keep `async/await` | Cosmetic issue, not functional; defer to later refactor |
| M5 topic handling | Two-query approach with structured topic data | Best UX: primary topic, count, all topics for popover |
| Migration strategy | Drizzle `migrate()` with `drizzle-kit generate` | Proper migration history, handles schema evolution |

---

## Section 1: Schema & DDL Unification

**Fixes**: C1 (Dual Source of Truth), L2 (No Migration Strategy)

### Problem

`database/index.ts:createTables()` contains ~220 lines of hand-written SQL DDL that duplicates and drifts from the Drizzle schema in `database/schema.ts`. Differences already exist:
- Schema defines `keyEntities` as `blob` (JSON mode), DDL has `TEXT`
- Schema defines `emailType` with enum constraint, DDL has no `CHECK`
- Any schema change requires editing two places

### Solution

1. **Delete** all raw SQL from `createTables()` and `createIndexes()` (~200 lines)
2. **Delete** the unused `import { app } from 'electron'` (also fixes L1)
3. **Run** `drizzle-kit generate` to produce initial migration SQL from `schema.ts`
4. **Replace** `initialize()` to call `migrate(drizzleDb, { migrationsFolder })` from `drizzle-orm/better-sqlite3/migrator`

### Existing Database Handling

For databases where tables already exist (created by the old raw DDL):
- Use `drizzle-kit push` for the first deployment (detects existing tables, applies only diffs)
- After the initial sync, switch to `migrate()` for all subsequent schema changes
- Alternatively, insert a migration journal entry marking the initial migration as applied

### Files Changed

- `database/index.ts` — delete `createTables()`, `createIndexes()`, refactor `initialize()`
- `database/migrations/0001_initial.sql` — new file, generated by `drizzle-kit generate`
- `drizzle.config.ts` — ensure it exists and is configured for better-sqlite3

## Section 2: Timestamp Standardization

**Fixes**: C2 (Silent Date Corruption)

### Problem

All timestamp columns use `mode: 'timestamp'` (expects seconds), but:
- Seeders write `Date.now()` (milliseconds)
- DDL defaults use `strftime('%s', 'now') * 1000` (milliseconds)
- Drizzle reads milliseconds as seconds, multiplies by 1000, producing dates in year 56000+

`TimelineRepository.toRecord()` has a hack (`createdAt.getTime() / 1000`) to compensate. Other repositories (EmailsRepository, TopicsRepository, DealsRepository, SummariesRepository) do NOT have this hack, meaning they return corrupt dates to the frontend.

### Solution

1. **Change** every `mode: 'timestamp'` to `mode: 'timestamp_ms'` in `database/schema.ts` (17 columns across 10 tables)
2. **Remove** the `/1000` timestamp hack in `TimelineRepository.toRecord()` (lines 406-419)
3. **Simplify** `toRecord()` to handle `Date` directly (Drizzle `timestamp_ms` returns `Date` objects)

### Why No Data Migration

The raw data in the database is already in milliseconds. The bug is in the READ path (Drizzle interpreting ms as seconds), not the WRITE path. Changing `mode` fixes the read path. No data transformation needed.

### Files Changed

- `database/schema.ts` — 17 column definitions change `mode: 'timestamp'` to `mode: 'timestamp_ms'`
- `core/repositories/timeline.ts` — remove `/1000` hack in `toRecord()`

## Section 3: Type Safety

**Fixes**: C3 (@ts-nocheck), M1 ($inferInsert), M2 (Duplicate Types)

### Problem

- `emails.ts`, `timeline.ts`, `labels.ts` have `// @ts-nocheck` at line 1, hiding all type errors
- `database/types.ts` uses `$inferInsert` (all fields optional) instead of `$inferSelect` (fields required after SELECT)
- `DealRecord`, `DealValueType` defined in both `database/deals.ts` and `core/repositories/deals.ts`
- `SeedEmail` defined in two seeder files

### Solution

1. **Remove** `// @ts-nocheck` from all three repository files
2. **Fix** all type errors revealed by the TypeScript compiler
3. **Rewrite** `database/types.ts` to use `$inferSelect` for read types, keep `$inferInsert` for write types (or export both)
4. **Consolidate** duplicate types:
   - Keep `DealRecord` in `database/deals.ts` (already uses `$inferSelect`), import in `core/repositories/deals.ts`
   - Keep `DealValueType` in `database/deals.ts` only
   - Keep one `SeedEmail` in one seeder, import in the other

### Files Changed

- `core/repositories/emails.ts` — remove `@ts-nocheck`, fix type errors
- `core/repositories/timeline.ts` — remove `@ts-nocheck`, fix type errors
- `core/repositories/labels.ts` — remove `@ts-nocheck`, fix type errors
- `database/types.ts` — switch to `$inferSelect` for read types
- `core/repositories/deals.ts` — import types from `database/deals.ts`, remove local duplicates
- `database/seed.ts` or `database/seeder.ts` — remove duplicate `SeedEmail`

## Section 4: Functional Bugs

**Fixes**: M3 (Broken count), M4 (Dead code), M6 (Broken WHERE), M7 (Wrong seed column)

### M3: Labels count() returns ID, not count

**Problem**: `select({ count: schema.gmailLabels.id })` returns the first label's ID value (e.g., `"label-1"`), not a count. UI shows "0" or "NaN" for label count.

**Fix**:
```ts
select({ count: sql<number>`count(*)` })
```

**File**: `core/repositories/labels.ts:228-234`

### M4: Dead code in getTopicDetail

**Problem**: `const inClause = allTopicIds.map(() => '?').join(',')` is built but never used. The actual query uses Drizzle's `inArray()`.

**Fix**: Delete the unused variable.

**File**: `core/repositories/topics.ts:361`

### M6: findExpiring compares integer vs ISO string

**Problem**: `dealExpiry` (integer milliseconds) compared against ISO date string `"2026-04-04"`. SQLite's type affinity: integer < text is always TRUE. Returns ALL active deals regardless of `withinDays`. User sees deals expiring in 6 months in the "expiring soon" section — urgency signal completely lost.

**Fix**: Compare millisecond timestamps to millisecond timestamps:
```ts
const expiryMs = expiryDate.getTime();
// In the query:
sql`${schema.deals.dealExpiry} <= ${expiryMs}`
```

**File**: `core/repositories/deals.ts:202-219`

### M7: seed.ts writes emailCount to update_count column

**Problem**: The 6th parameter maps to `update_count` but receives `sender?.emailCount || 1`. A sender with 50 emails shows "Updated 50 times" on their summary — misleading.

**Fix**: Replace with `1`:
```ts
insertSenderSummary.run(`ss-${...}`, domain, summary, wordCount, Date.now(), 1);
```

**File**: `database/seed.ts:227`

## Section 5: Timeline Duplicate Rows

**Fixes**: M5 (findAll produces duplicates)

### Problem

`findAll()` LEFT JOINs `emailTopics` and `topics`. If an email has 3 topics, the query returns 3 identical rows for the same timeline update (one per topic). No deduplication applied.

### User Experience Requirements

1. Show one card per email in the timeline — not duplicates
2. Show a primary topic badge on each card
3. If the email has multiple topics, show "+N more" indicator
4. Hovering over "+N more" shows a popover with all topic associations
5. When a topic filter is active, the displayed primary topic should be the matching one

### Solution: Two-Query Approach

**Query 1**: Get timeline updates with sender info (no topic join = no duplicates):
```ts
const updates = await db.select({
  /* timeline fields + email fields */
})
.from(timelineUpdates)
.innerJoin(emails, eq(timelineUpdates.emailId, emails.id))
// NO topic join here
.orderBy(desc(timelineUpdates.createdAt));
```

**Query 2**: Get topics for all emailIds in the result:
```ts
const emailIds = updates.map(u => u.emailId);
const topicRows = await db.select({
  emailId: emailTopics.emailId,
  topic: topics.fullPath,
  confidence: emailTopics.confidenceScore,
})
.from(emailTopics)
.innerJoin(topics, eq(emailTopics.topicId, topics.id))
.where(inArray(emailTopics.emailId, emailIds));
```

**Merge**: Build a map and attach to records:
```ts
interface TopicInfo {
  primary: string;       // The topic to display
  count: number;         // Total number of topic associations
  all: string[];         // All topic paths
}
```

The `TimelineUpdateRecord.topic` field changes from `string | null` to `TopicInfo | null`.

### Frontend Changes

- **Topic badge**: Display `topic.primary`
- **"+N more" indicator**: Show when `topic.count > 1`
- **Hover popover**: Display `topic.all` list
- **Filter-aware primary**: When topic filter is active, set `primary` to the matching topic from `all`

### Files Changed

- `core/repositories/timeline.ts` — refactor `findAll()` with two queries, update `TimelineUpdateRecord` type
- `src/components/screens/TimelineScreen.tsx` — update topic badge rendering, add "+N more" indicator
- `src/components/views/EmailDetailView.tsx` — update topic display

## Section 6: Schema Corrections

**Fixes**: H4 (Missing Composite PKs), H5 (Missing Self-Referencing FK)

### H4: Add Composite Primary Keys to Junction Tables

**Problem**: `emailTopics` and `emailLabels` have no `.primaryKey()` in the Drizzle schema. `insert().onConflictDoNothing()` may not detect conflicts, allowing duplicate associations.

**Fix**:
```ts
export const emailTopics = sqliteTable('email_topics', {
  emailId: text('email_id').references(() => emails.id, { onDelete: 'cascade' }).notNull(),
  topicId: text('topic_id').references(() => topics.id, { onDelete: 'cascade' }).notNull(),
  confidenceScore: real('confidence_score'),
}, (table) => [
  primaryKey({ columns: [table.emailId, table.topicId] }),
]);

export const emailLabels = sqliteTable('email_labels', {
  emailId: text('email_id').references(() => emails.id, { onDelete: 'cascade' }).notNull(),
  labelId: text('label_id').references(() => gmailLabels.id, { onDelete: 'cascade' }).notNull(),
}, (table) => [
  primaryKey({ columns: [table.emailId, table.labelId] }),
]);
```

### H5: Add Self-Referencing FK on topics.parentId

**Problem**: `parentId` has no FK reference. Deleting a parent topic leaves children with orphaned references. User sees broken topic hierarchies.

**Fix**:
```ts
parentId: text('parent_id').references((): typeof topics => topics.id, { onDelete: 'set null' }),
```

With `onDelete: 'set null'`, child topics become top-level when their parent is deleted.

### Files Changed

- `database/schema.ts` — add composite PKs to `emailTopics`, `emailLabels`; add FK to `topics.parentId`

## Section 7: Transactions

**Fixes**: H1 (No Transactions on Multi-Table Operations)

### Problem

No repository uses `db.transaction()`. Multi-table operations (insert email + timeline + deals + topics + labels) are not atomic. A crash mid-operation leaves partial data. The user could see an email with a timeline update but no topic association.

### Solution

Wrap critical multi-table operations in `db.transaction()`:

1. **Email processing pipeline**: Insert email + timeline_update + deals + topics + labels
2. **linkLabelsToEmail**: Delete existing + re-insert
3. **Summary updates**: Read current summary + update

Example:
```ts
await this.db.getDatabase().transaction(async (tx) => {
  await tx.insert(schema.emails).values(emailData);
  await tx.insert(schema.timelineUpdates).values(timelineData);
  if (dealData) await tx.insert(schema.deals).values(dealData);
  for (const topic of topics) await tx.insert(schema.emailTopics).values(topic);
});
```

### Files Changed

- All repository files with multi-table writes

## Section 8: Dead Code & Cleanup

**Fixes**: H2 (Dead Channel Definitions), L1 (Unused Electron Import)

### H2: Remove Dead DB Channels

**Problem**: `channels.ts` defines `DB_GET_TIMELINE`, `DB_GET_TOPICS`, `DB_GET_SENDERS`, `DB_GET_TOPIC_SUMMARY`, `DB_GET_SENDER_SUMMARY`. These are never used — the actual IPC uses different channel names (`timeline:list`, `topics:list`, etc.) registered in `electron/main.ts`.

**Fix**: Remove the dead entries from the `CHANNEL` constant:
```ts
// Delete these lines:
DB_SEED: 'db:seed',
DB_GET_TIMELINE: 'db:getTimeline',
DB_GET_TOPICS: 'db:getTopics',
DB_GET_SENDERS: 'db:getSenders',
DB_GET_TOPIC_SUMMARY: 'db:getTopicSummary',
DB_GET_SENDER_SUMMARY: 'db:getSenderSummary',
```

### L1: Remove Unused Electron Import

**Problem**: `database/index.ts` imports `app` from Electron but never uses it. Couples the database layer to Electron, preventing testing outside the main process.

**Fix**: Remove `import { app } from 'electron'`. (Already addressed by Section 1 when `createTables()` is deleted.)

### Files Changed

- `electron/ipc/channels.ts` — remove dead `DB_*` entries from CHANNEL constant
- `database/index.ts` — remove unused `app` import (covered by Section 1)

## Implementation Order

The sections have dependencies. Implement in this order:

1. **Section 2** (Timestamps) — changes `schema.ts` column modes
2. **Section 6** (Schema corrections) — changes `schema.ts` table definitions
3. **Section 1** (DDL unification) — generates migrations from the now-correct schema
4. **Section 3** (Type safety) — removes `@ts-nocheck`, fixes types
5. **Section 4** (Functional bugs) — fixes logic in repositories
6. **Section 5** (Timeline duplicates) — refactors `findAll()` and frontend
7. **Section 7** (Transactions) — wraps multi-table operations
8. **Section 8** (Dead code) — final cleanup

Sections 2 and 6 must come before Section 1 because migrations are generated from the schema. Sections 3-5 can be done in parallel after Section 1.

## Risk Assessment

| Risk | Mitigation |
|------|------------|
| Existing DB tables conflict with first migration | Use `drizzle-kit push` for initial transition |
| Removing timestamp hack before schema change breaks timeline dates | Change schema.ts and remove hack in same commit |
| `@ts-nocheck` removal reveals many type errors | Assess errors before fixing; may reveal real bugs |
| M5 type change (`topic: string` → `TopicInfo`) breaks frontend | Update all consumers in same PR |
| Transactions add overhead to synchronous SQLite | Negligible; better-sqlite3 transactions are fast |
